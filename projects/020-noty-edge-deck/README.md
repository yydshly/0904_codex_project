# Noty Edge Deck：屏幕边缘的低打扰交互实验

> 参考 Noty 的核心交互，自主实现一个可在浏览器体验的“静默驻留 → 层叠展开 → 即时编辑”概念 Demo，并判断这种界面适合放在哪里、下一步可以长成什么。

## 为什么值得单独做一个子项目

Noty 表面上是便签应用，真正值得研究的是它提供了一种不同于 Dock、菜单栏和普通侧边栏的入口：**界面占据屏幕边缘的极小区域，需要时迅速展开，完成操作后自动退场**。

这种设计解决的不是“如何编辑更多内容”，而是三个更通用的问题：

1. 如何让高频工具随时可达，但不持续占用注意力。
2. 如何在不离开当前应用或任务的情况下完成短操作。
3. 如何用空间位置和动画帮助用户理解界面的状态变化。

因此，本项目没有复制 Noty 的品牌、素材或源码，而是把它的交互模式抽出来，做成可直接体验和继续扩展的 Web 原型。

## Demo 实现了什么

- **Rest**：右侧只保留一条窄胶囊和彩色短线。
- **Fan**：悬停、聚焦或点击后，便签沿屏幕边缘层叠展开。
- **Expanded**：点击卡签后，便签纸从卡组向左拉出。
- **即时编辑**：标题和正文可以修改，停止输入后写入 localStorage。
- **新建与置顶**：支持创建空白便签；置顶后点击背景不会收起。
- **恢复路径**：关闭按钮、点击背景或 Esc 可以逐层退出。
- **跨表面适配**：桌面使用右侧边缘，手机转换为底部托盘。
- **可访问性**：语义化按钮、可见键盘焦点、Escape 恢复、reduced-motion。
- **主题**：浅色与深色模式都保持卡组和纸张的层级关系。
- **显式体验入口**：首屏按钮可以直接展开卡组，不必先发现极窄的屏幕边缘热点。
- **Windows 实现蓝图**：页面内展示界面、Tauri 宿主、Win32 窗口层和本地数据四层架构，以及 Rest/Fan/Expanded 的窗口状态映射。
- **业务与扩展地图**：用捕获、召回、关注、轻操作四类场景判断适配度，并给出 P0–P3 的演进路线。

Web 版本模拟的是交互和产品概念，不具备原生 macOS 的全局快捷键、多显示器、跨 Space 浮动窗口和系统级点击监听。

## 本地运行

```powershell
cd E:\0904_codex_project\projects\020-noty-edge-deck\demo
python -m http.server 4173
```

打开 <http://127.0.0.1:4173>。

建议体验顺序：

1. 点击“立即体验卡组”，或将鼠标移动到右侧彩色短线。
2. 点击任意便签卡签。
3. 修改标题和正文，观察保存状态。
4. 点击菱形按钮保持展开，再点击背景。
5. 按 Esc 逐层收起卡片。
6. 切换深浅主题，并把浏览器缩到 390px 观察底部托盘。
7. 继续向下阅读 Windows 实现、业务场景和扩展路线。

## 从 Noty 抽取出的核心模式

```text
低存在感入口
      ↓
可预期的空间展开
      ↓
一次只处理一个轻量对象
      ↓
即时保存与清晰恢复
      ↓
自动退场，回到原任务
```

关键不是某个圆角或动画参数，而是入口、状态和退出机制共同降低了上下文切换成本。原项目通过 AppKit `NSPanel`、`NSTrackingArea`、三态控制器和多显示器管理实现系统级体验；本 Demo 使用固定定位、CSS 空间层级和浏览器事件复现同一套认知模型。

## 适合的场景

### 1. 高频、短时、跨应用的信息

- 会议中的临时行动项。
- 开发时要反复查看的命令、接口参数和测试账号说明。
- 写作、设计、研究时暂存的素材与引用。
- 客服或销售需要随时调用的话术片段。

共同特征是：内容不复杂，但频繁离开当前窗口去寻找它的成本很高。

### 2. 需要“看得见但不打扰”的状态

- 构建、上传、渲染等长任务状态。
- 今日最重要的三件事。
- 会议计时和下一议题。
- 直播、演示、全屏工作时的私人提示。

这类信息适合以色点、短标签或数量提示驻留；只有发生变化或用户主动靠近时才展开。

### 3. AI 助手的环境式入口

- 随手捕获一段待总结文本。
- 展示 Agent 的待确认事项和执行结果。
- 根据当前项目召回相关上下文卡片。
- 把会议记录自动提取为下一步行动。

相比一直打开聊天窗口，边缘卡组更像一个“环境式收件箱”：输入和结果可以暂存，用户仍留在原任务里。

### 4. 垂直工具的轻量控制面

同一模式还可以用于剪贴板历史、常用文件、截图、计时器、翻译结果、开发环境切换和快捷动作。此时“便签”只是卡片的一种类型。

## 不适合的场景

- 长文档、复杂表单和需要持续深度编辑的任务。
- 大量层级导航或几十个并列对象。
- 必须一次比较多份内容的分析界面。
- 强提醒、紧急告警和不能自动消失的关键操作。
- 在窄屏上仍强行复制桌面右侧 hover 交互。

边缘入口的价值来自克制；当主任务本身已经复杂时，应跳转到完整工作区，而不是继续扩大浮层。

## 可扩展方向

| 优先级 | 方向 | 具体能力 | 关键代价 |
| --- | --- | --- | --- |
| P0 | 组件化 | 把 Deck、Tab、Panel、状态机和持久化适配器拆成独立模块 | 需要先去掉当前 Demo 中的直接 DOM 依赖 |
| P0 | 数据可靠性 | IndexedDB、版本迁移、导入导出、撤销和恢复 | 必须设计失败提示，不能静默丢失数据 |
| P1 | 卡片类型 | 便签、任务、剪贴板、文件、运行状态、快捷动作 | 需要统一卡片协议和权限边界 |
| P1 | 检索组织 | 标签、分组、全文搜索、最近使用和固定卡片 | 条目增多后需要从“扇形列表”进入完整管理页 |
| P1 | 系统入口 | macOS App Intents、Raycast、Alfred、浏览器扩展、Share Extension | Web Demo 无法提供真正的全局入口 |
| P2 | 上下文感知 | 按当前应用、项目、窗口或 URL 显示关联卡片 | Accessibility 和浏览器权限会改变信任模型 |
| P2 | AI 增强 | 自动分类、摘要、任务提取、语义召回、Agent 审批 | 应默认本地处理，远程调用需要显式授权 |
| P2 | 多端同步 | macOS、Windows、iOS 与 Web 同步 | 需要端到端加密、冲突合并和设备密钥管理 |
| P3 | 团队工作 | 共享卡组、评论、分派、状态订阅 | 产品会从个人工具转向协作系统，复杂度显著上升 |

## 建议的产品路线

### 阶段一：验证入口，而不是扩充编辑器

先用当前 Demo 做可用性测试，关注：用户是否能发现入口、展开是否误触、完成记录需要多久、界面能否自然退场。核心指标应是调用成本和返回原任务的速度。

### 阶段二：建立统一的卡片协议

将卡片抽象为 `type + title + preview + payload + actions + context`。便签、任务、AI 结果和运行状态都使用同一套卡组与打开逻辑，详情内容由不同渲染器负责。

### 阶段三：增加上下文与智能

入口稳定后，再引入当前应用、项目或 URL 上下文，并使用本地索引进行召回。AI 应负责减少整理成本，而不是让每次记录都变成一次等待远程模型的流程。

### 阶段四：完整工作区承接复杂任务

边缘卡组只负责捕获、预览、选择和轻操作。搜索、批量整理、关系管理和协作进入独立工作区，从而保持边缘界面的克制。

## 局限与边界

- 它是概念验证，不是可安装的桌面应用。
- 浏览器页面只能在当前标签页内工作，不能覆盖其他应用。
- 只保留最多五张可见卡签，更多条目的管理界面尚未实现。
- localStorage 适合演示，不适合敏感数据、大型附件或多端同步。
- 当前没有删除、归档、搜索和数据导出，避免把原型扩成未经验证的完整笔记产品。
